### Reflection
 
Agreeing ways of working in the first meeting helped the team. Because I had read the brief beforehand, we could spend the meeting planning rather than explaining the task, and we left with a clear next step: everyone would brainstorm requirements individually, then collate them the following week. The risk is that a plan agreed in one hour can leave details vague, so we will need to revisit it as the project develops.
 
EARS changed how I wrote my requirements. My first drafts were loose and could be read in more than one way. EARS gave me a fixed sentence structure, which forced me to state the trigger, the condition and the expected system response. The requirements became shorter, more specific and easier to test. It also helped me separate functional from non-functional requirements, as some of my early ideas, such as how fast or easy to use something should be, belonged in the non-functional category. 

## WC 19/10/26
 
### Diary
 
* **20/10**
  * Compiled the team's requirements into a single file
  * Committed the combined requirements file to main
  * Checked the combined list for duplicates and overlaps between team members' requirements
### Reflection
 
Everyone had brainstormed requirements separately, so the individual lists used different wording, different levels of detail and some overlapping ideas. Bringing them into one file meant deciding how to group them and where requirements were duplicates or conflicted. Because we had used EARS, the requirements were already in a similar structure, which made comparing them much easier than it would have been with free-form notes.
 
Using Git helped with this task. Committing the combined file to main gave the team one agreed version to work from, with a clear record of who added it and when. Earlier versions were preserved, so nothing was lost if we later changed how requirements were grouped.
 
I learned that it is important to preserve what each person meant rather than rewriting it to suit my own style. Where a requirement was unclear, the better approach is to check with the author than to guess, which is harder to do asynchronously and takes more time.
 
Next time, I would agree a naming and formatting convention for requirements before everyone starts writing, and set a deadline for contributions so that collating is a single quick step rather than waiting on late additions.

  * Checked the draft dashboard against the requirements and noted where charts or labels needed changing
  * Updated the dashboard and committed the changes to the repository
  * Helped plan the video: agreed the key findings to show and who would cover each section
  * Wrote part of the video script and recorded my section
  * Reviewed the team's dashboard and video and gave feedback before they were finalised
  
### Reflection
 
The main challenges of working remotely and asynchronously were finding times when everyone was free, waiting for replies that held up other work, and making sure everyone was working from the latest version of shared files. Without being in the same room, it is also easy to misread tone or assume someone has seen a message when they haven’t.

I handled these by keeping work in shared online tools and the Git repository rather than in private files, so there was one agreed version of each document. Agreeing who would do what, and by when, reduced waiting, and written updates meant the team didn’t depend on everyone attending every meeting. This only worked when people kept their updates current, so it relied on everyone’s discipline.

Next time, I would set up the shared tools and agree communication habits on day one, record decisions as they happen rather than afterwards, and arrange short regular check-ins earlier so that problems surface sooner.
